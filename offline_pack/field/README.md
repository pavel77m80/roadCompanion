# Field GPS Validation — инструменты полевой проверки

Проверка Offline Story Pack + GPS Playback на реальном GPS-треке проезда
по маршруту бандла. Движок `companion_core` и параметры НЕ изменяются.

**Статус: ПОЛЕВОЙ ТЕСТ ВЫПОЛНЕН.** Реальный трек `experiment/20261010-080834.gpx`
пром. `field_track_20261010.json`. Итог — в `field_report.md` / `field_report.json`
и `calibration_report.json` (рекомендация: baseline без изменений). Движок и
параметры не менялись. Сырые треки (координаты поездки) в git не коммитятся —
только агрегированные отчёты.

## Файлы

| Файл | Назначение |
|---|---|
| `preflight_baseline.py` | снимок параметров движка и контрольные данные до изменения чего-либо |
| `baseline_report.json` | результат preflight (baseline) |
| `record_gps.html` | браузерный GPS-рекордер (офлайн, точный, экспорт JSON/GPX) |
| `track_schema.example.json` | пример канонического трека `field_track_v1` |
| `import_track.py` | импорт `.gpx` / `.nmea` / `.json` в `field_track_v1` |
| `replay_track.py` | replay трека через движок без его изменения |
| `metrics_report.py` | метрики качества по POI + отчёты `field_report.{json,md}` |
| `calibrate.py` | калибровка ограниченным набором вариантов, baseline не меняется |
| `field_report.json` / `.md` | итоговый отчёт полевой проверки |
| `calibration_report.json` | итог калибровки |

## Порядок работы

### 1. Базовый прогон (baseline) — уже выполнен

```powershell
python -X utf8 offline_pack/field/preflight_baseline.py
```

### 2. Запись реального трека

Безопасность (обязательно):
- во время движения приложением НЕ пользуемся; рекордер включает пассажир
  **до** старта, телефон закреплён и не требует взаимодействия;
- запись ведётся по всему маршруту бандла `trip_bundle`, включая заезд и
  выезд за крайние точки (по 500 м запас с каждой стороны).

Варианты записи:
- `record_gps.html` — открыть в браузере смартфона на HTTPS/локально,
  нажать «Начать запись», в конце «Остановить» и «Скачать JSON» (или GPX).
  Работает офлайн, данные не покидают устройство.
- любые GPS-логгеры, экспортирующие `.gpx` (Strava, OsmAnd, GPS Logger, …),
- NMEA-лог (`.nmea` / `.log`).

Требования к треку: включённые координаты (не пустой трек), метки времени,
по возможности PDOP/HDOP или accuracy. Экспорт БЕЗ сглаживания.

### 3. Импорт

```powershell
python -X utf8 offline_pack/field/import_track.py <файл.gpx|.nmea|.json>
```

Результат — `*.track.json` (схема `field_track_v1`). Присутствие пропусков
фиксаций нормально: они помечаются `missing=true`, а не нулями, и будут
пропущены при replay.

### 4. Replay через движок

```powershell
python -X utf8 offline_pack/field/replay_track.py <трек.track.json>
```

Каждое событие движка привязано к исходной фиксации (`source_index`,
`timestamp_utc`, координаты, точность). Отброшенные/пропущенные фиксации —
в `skipped_fixes` с причиной. Сетевых запросов нет.

### 5. Метрики

```powershell
python -X utf8 offline_pack/field/metrics_report.py <replay.json> <трек.track.json>
```

Без аргументов генерирует BLOCKED-отчёт. Расчёт:
- по каждому POI — минимальное расстояние трека, расстояние в момент
  срабатывания, точность GPS, отброшенные фиксации рядом, повторные
  срабатывания, класс (проехал / проехал по прямой, но вне маршрута / не
  проехал / неопределённо по GPS), раннее/позднее срабатывание;
- доли и распределение, число неопределённых случаев;
- единая метрика «12 из 12» не используется без проверки, что трек вообще
  проходил в радиусе.

### 6. Калибровка (при необходимости)

```powershell
python -X utf8 offline_pack/field/calibrate.py <трек.track.json>
```

Сравнивается ограниченный набор: baseline, `radius_x0.8`, `radius_x1.3`,
`off_route_200`, `off_route_300`. Выбирается минимальное изменение, baseline
сохраняется и остаётся первым. При недостатке данных — рекомендуется baseline.

## Итоги полевого теста (10.10.2026)

Трек `20261010-080834` (GPS Logger, 2583 фиксации, 43 мин, непрерывный,
1 с интервал). Покрытие маршрута: прогресс 168 → 25414 м из 25603 м.

Важное допущение: **рекордер не сохранил точность GPS (нет HDOP/accuracy)**,
поэтому при импорте (`--assume-accuracy-m 10`) фиксациям присвоено допущение 10 м (явно записано в
`field_track_20261010.json` → `assumptions.accuracy` и повторено в отчёте).
Это допущение, а не измерение; порог отбраковки движка 50 м, поэтому на
вердикты триггеров выбор допущения не влияет.

Результат:
- 5 POI классифицированы `passed_near` (трек был на маршруте в радиусе) —
  **все 5 сработали** (доля ожидаемых 1.0);
- 6 POI `near_crow_flies_but_offroad` (водитель ехал параллельным путем,
  движок был в режиме съезда; 2 из них всё же сработали) — см. таблицу;
- 1 POI `not_passed` (не проезжал в радиусе) — несрабатывание корректно;
- 73 фиксации (2.8%) отклонены по `teleport_jump` (навигационный шум/заезды);
- повторных срабатываний 0, неопределённых GPS-случаев 0;
- калибровка: все варианты дают score=1.0, **рекомендация: baseline без
  изменений** (минимальное изменение; параметры не подгоняются).

## Честность отчёта

- отсутствие срабатывания НЕ считается ошибкой, если трек не проходил в
  радиусе;
- неопределённые случаи выносятся отдельно;
- нет единой метрики «12/12» без проверки близости трека;
- синтетические/примерные данные помечаются как таковые (`is_real_car_drive`
  у примерного трека установлен в `false` или в `track_id` указан `sample`);
- в отчёт не включаются домашние координаты и персональные данные.
